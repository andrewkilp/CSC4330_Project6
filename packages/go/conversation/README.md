# Pure conversation state (#4)

`state.go` performs no network, audio, database or clock work. `New()` (or the zero value) is a draft call. All State commands return a new `State` and leave their input unchanged, including on failure. Callers must retain the returned value. The separate orchestration layer in `loop.go` executes provider work and cancellation, allocates UUIDs and timestamps, and keeps a local response journal.

Call lifecycle: draft -> dialing -> connected -> ended/failed/cancelled. A draft or dialing call can also become terminal. Connected has a separate paused flag; it is never encoded as a new call status. Terminal states cannot reopen. An identical status callback is idempotent; earlier or otherwise invalid callbacks return `ErrInvalidTransition`.

Responses go generating -> suggested -> approved -> speaking -> spoken. An active response can fail; pause, instruction, interruption and terminal end cancel any active response. Spoken/failed/cancelled response records remain available as history in the snapshot, but cannot advance. Beginning the next response allocates a new generation token. Response IDs are generated/validated by the future API boundary.

`ApplyInstruction(expectedRevision)` advances the context revision and invalidates current work. It accepts an instruction while paused without resuming. The repository/action handler owns idempotency keys; this pure function only enforces the expected revision. `Interrupt()` fences generation and queued speech without changing the goal revision. Pause fences work too; resume never revives it.

Every asynchronous completion must present its response ID and the `Token` returned by `BeginResponse`. The token carries context revision and generation. Check the call identity as well; tokens are only scoped to one machine. Never use a token as authentication. Only an approved response can start speaking, and only a speaking response can become spoken. A late approval, generation callback or playback acknowledgement cannot advance an obsolete response.

This is the decision layer, not a cancellation executor. The orchestrator must serialize access to each call and, on invalidation, cancel contexts and clear provider audio buffers. This module does not promise thread safety for a shared caller variable or stop a provider itself. Persistent state restoration, text validation, approval policy and request idempotency belong to later issues.

Run `moon run conversation:build conversation:lint conversation:test`. The table tests exercise lifecycle transitions, pause/resume, dialing cancellation, stale revisions, response approval and late callbacks.

## Mock conversation loop (#19)

`NewLoop(callID, goalJSON, responder)` creates one call's in-memory orchestrator. Transition it through dialing to connected, then pass partial/final business turns to `ObserveBusinessTurn`. Partial updates replace by turn ID; finalized turns cannot change, and identical final replay does not call the provider again. Only final business turns trigger generation. All Responder inputs contain finalized business text and a separate ordered private instruction list. Assistant transcript ingestion follows playback acknowledgement in #30; this loop never creates assistant speech or transcript entries.

The local `Responder` interface uses #14's existing `claude.Input`/`claude.Update` signature, so `*claude.Client` already implements it. This is an explicit temporary integration boundary pending the shared interfaces in #6, not an implementation of the other provider adapters. `mock.NewConversation` explicitly injects a network-free scripted responder for mock calls. Real calls must supply their configured responder; this layer never silently falls back to a mock.

The loop publishes `response.updated` envelopes from generating through suggested, always with `needs_approval: true`. Generation stops for operator review, including uncertain approval mode. #29 adds the explicit `ApproveResponse` and server-only `SynthesizeApproved` operations described below; neither runs implicitly. Only a successful Generate return after a valid Final callback can become suggested; missing finals, partial failures, invalid revisions and text over 1500 characters become failed with cleared text and a fixed user-safe error. The provider error body is never included. Inputs are capped at 200 business turns, 100 instructions, 16 KiB goal JSON and the Claude adapter's transcript/instruction limits. Each generation has a 30-second context deadline, and the local journal is bounded to 4096 response events; a full journal rejects further generation until the call is closed. A responder must honor context cancellation and return promptly.

`Instruct` advances the in-memory revision, cancels the previous context and regenerates from current finalized turns. It is a hook for #28's future atomic, idempotent repository command, not a durable instruction endpoint. `Pause`, `Interrupt`, new remote speech and terminal `Transition` cancel outstanding generation. Instructions received while paused do not generate until `Resume`. All callbacks check the response ID and generation/revision token, so a provider that returns late cannot overwrite new state. Provider work executes outside the lock. Operations may run concurrently; generation-bearing operations block until the provider returns and should be given a cancellable request context. Call transitions and instruction persistence/event publication remain the owning tasks' responsibility.

`Events()` returns a detached local response-only journal, not persisted events, cross-entity sequence allocation or SSE replay. #23 must replace local sequencing with the durable per-call event allocator during integration. `ApproveResponse` binds an optional edited reply to one suggested response/revision with local retry deduplication. `SynthesizeApproved` hands that stored text to a configured synthesizer once, with cancellation and token checks. It does not mark playback or create spoken turns. See [approval integration notes](../handlers/responses/README.md) for owner checks, pending persistent storage, downstream queue fencing and #30 responsibilities.

From the repo root, `moon run api:dev -- --mock-scenario restaurant-time-conflict` (or `appointment-missing-detail`) prints actual generated response events and exits at the first suggested reply. The command logs that all data is fictional mock data. It replays only business turns up to that boundary, never the fixture's approval or playback events. Without the explicit flag, the API still serves its existing routes. No provider credentials, calls or audio are involved.
